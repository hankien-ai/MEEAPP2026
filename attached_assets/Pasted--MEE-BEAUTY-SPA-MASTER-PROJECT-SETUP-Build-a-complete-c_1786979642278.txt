# MEE BEAUTY SPA — MASTER PROJECT SETUP

Build a complete, clean, scalable **Spa Management Web Application** called **MEE BEAUTY SPA**.

This first task is ONLY to create the complete application foundation/app shell.

The application must be fully navigable and visually functional, but detailed business logic will be implemented module-by-module later.

Do NOT try to fully implement all business logic in this first task.

---

## 1. TECHNOLOGY STACK — MUST FOLLOW

Use exactly:

* React
* Vite
* TypeScript
* Tailwind CSS
* shadcn/ui
* React Router
* Supabase
* PostgreSQL through Supabase
* Supabase Storage
* Supabase Realtime
* Vercel-compatible deployment

Do NOT migrate to Next.js.

Do NOT introduce another frontend framework.

Use a clean TypeScript architecture.

---

# 2. DEVELOPMENT PRINCIPLE

This application will be developed progressively.

The first version must behave like a **complete empty application shell**.

Think of it as:

> "A fully designed and architected application with empty modules, ready to be implemented one module at a time."

Every major module must already have:

* Route
* Page
* Layout
* Navigation item
* Empty state
* Loading state
* Error state where appropriate
* Basic reusable components
* Proper TypeScript types
* Module-specific folder structure

Do NOT implement complicated business logic yet.

Do NOT create fake business logic that will later conflict with the real implementation.

Mock/demo data may be used only where needed to make the interface visually functional.

Clearly separate mock data from future Supabase data access.

---

# 3. CORE ARCHITECTURE

Use a modular architecture.

DO NOT put the entire application into App.tsx.

DO NOT create giant files.

DO NOT mix unrelated business logic.

Recommended structure:

```text
src/
├── app/
│   ├── router/
│   ├── providers/
│   └── config/
│
├── modules/
│   ├── dashboard/
│   ├── customers/
│   ├── catalog/
│   ├── packages/
│   ├── pos/
│   ├── staff/
│   ├── attendance/
│   ├── loyalty/
│   ├── reports/
│   ├── booking/
│   ├── expenses/
│   └── settings/
│
├── components/
│   ├── ui/
│   ├── layout/
│   └── shared/
│
├── hooks/
├── lib/
│   ├── supabase/
│   └── utils/
│
├── services/
├── types/
├── validations/
└── data/
```

Each module should be independently organized.

For example:

```text
modules/customers/
├── pages/
├── components/
├── hooks/
├── services/
├── types/
└── validations/
```

Use the same pattern for other modules.

Shared components should contain ONLY genuinely shared functionality.

# 19. COMMISSION ARCHITECTURE

Prepare the application for two independent commission concepts:

## Sales commission

The staff member who sells a service/package may receive sales commission.

## Performance commission

The staff member who actually performs a service receives the commission configured for that service.

Important:

Performance commission is based on the ACTUAL SERVICE PERFORMED.

It does not matter whether the service came from:

* Direct purchase
* Package
* Gift service

The architecture must support:

```text
Seller
Performing Staff
Actual Service
Commission
```
